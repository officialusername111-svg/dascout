## The one thing that actually matters: prices are readable by anyone

**Status: open, pre-existing by months, NOT introduced by any recent run. Needs your decision before
anything can be built.**

The standing rule is *no peso amounts anywhere public*. It is enforced only by the application never
selecting the column. **The database grants `anon` table-level SELECT on `public.listings`, so every
column is readable directly.** The publishable key ships in the client bundle, so it is public by
design. Reproduce it in one line:

```bash
curl -H "apikey: <the key in the public site's JavaScript>" \
  "https://kogpuuidawbmttyswvsx.supabase.co/rest/v1/listings?select=id,price_php&status=eq.live"
```

That returns real prices for live listings. The two E2E specs that assert "no peso on the public
page" pass, and always would — they check rendered HTML, not the API surface. So the rule *looks*
enforced and is not.

**The obvious fix does not work.** A column-grant detach (the pattern
`20260730095404_listing_views_detach_column_grant` already uses on `listing_views`) would be:

```sql
revoke select on public.listings from anon;
grant select (<the columns the public site reads>) on public.listings to anon;
```

But `web/lib/queries.ts:350` — `getSpotlightListings`, the **rotating hero card on the home page** —
does `.order('price_php', { ascending: false })`. Ordering requires SELECT on the column. Revoke it
and the home-page hero breaks. It never *shows* the price; it ranks by it.

**Three options, and picking one is a product decision:**

1. **Change the hero's ordering** (to `published_at`, or `is_trending` alone) and then revoke.
   Simplest. Changes which listings get featured.
2. **Move the spotlight query behind a `SECURITY DEFINER` function** that ranks by price internally
   and returns only safe columns. Preserves today's behaviour; adds a function.
3. **Accept it** and restate the rule as "no prices *rendered* publicly", which is what is actually
   true today.

Whichever is chosen, the run needs a test that asserts the anon API **refuses** `price_php` while the
public pages still render — otherwise the same gap reappears silently.

Columns the public site genuinely needs, if you go with 1 or 2 (derived from `CARD_COLUMNS` plus
every filter, order and embed): `id, slug, title, category, area_detail, lot_area_sqm,
floor_area_sqm, bedrooms, bathrooms, is_trending, published_at, description, status, town_id,
created_at`. `search_vector` is **not** used by any public query. Getting this list wrong takes the
site down, which is why it was not attempted at the end of a long session.

Full record: `~/.claude/projects/D--Workspace-DaScout/memory/dascout-price-exposed-to-anon.md`.

## What shipped today

**1. The admin/staff privilege split — built, applied, and PROVEN.**

The brief said the split did not exist. It was worse: its absence was a live escalation hole, with
**two** routes, not one.

- *Route 1 (known):* `is_staff()` is true for both roles, `guard_profile_role()` gated role changes on
  `is_staff()`, and `profiles_staff_all` was `FOR ALL`. A staff user could PATCH their own row to
  `role='admin'`.
- *Route 2 (found mid-run, nobody had it):* the guard was `BEFORE UPDATE` only, so staff could delete
  their profile row and re-insert it as `admin` — and could delete the owner's row, permanently
  emptying the super-admin tier.
- *Also found:* `guard_profile_role()` was `SECURITY DEFINER`, so it saw *itself* as the caller on
  every call. The guard was effectively blind.

Closed in layers: the `role` column is revoked from every API-reachable role, the blanket policy is
gone, and the guard is now `SECURITY INVOKER`, fires on INSERT **and** UPDATE, and uses a
**fail-closed allowlist** (`pg_has_role(current_user,'postgres','member')`) rather than a denylist.

**13 escalation-denial tests execute against the live database and pass** —
`web/tests/vitest/admin-escalation-denial.integration.test.ts`. A staff session cannot promote itself
or anyone, cannot write any role, cannot insert or delete a profile row, cannot create an invite,
cannot demote, cannot read the invite table. It *can* still edit its own display name and manage every
listing — tested, so the lockdown is provably not over-broad.

**2. Super-admin invites.** 32 bytes of `gen_random_bytes`, stored only as a SHA-256 digest, single
use, 7-day expiry. `admin_invites` has **no write policy and no write grant for any client role** —
that is what does not repeat the `run-p5b` token trap, where the anon INSERT surface let a caller
craft a row and self-redeem. Redemption is a definer RPC granted to `authenticated` only, matching the
caller's own confirmed email read from `auth.users`.

**"Confirm email" is ENABLED** (`mailer_autoconfirm: false`, verified). The mailbox factor is real, so
the invite is genuinely two-factor. Note the trap: the three existing users are auto-confirmed with no
confirmation mail, because they were made via the dashboard, which auto-confirms regardless. The user
data suggested the setting was off; it isn't.

**3. Property number** — nullable text on `listings`, typed in by the admin, case-insensitively unique.
Wired through the form, the list and admin search. Clearing it stores `NULL`, not `''`, so cleared rows
don't collide.

**4. Role-change audit trail** — `admin_role_changes` records actor, target, both roles and the door it
came through, written in the same transaction as the role write. Append-only by construction: no write
policy, no write grant, only the definer RPCs write it.

## Things that will bite you if you don't know them

- **`web/AGENTS.md` is real.** This is Next.js **16.2.12** and it is not the Next.js in your training
  data. Read `web/node_modules/next/dist/docs/` before using any Next API.
- **There is no Docker and no local Postgres on this machine.** The only reachable database is
  **production**. A migration cannot be rehearsed locally — it is applied via the Supabase MCP, at the
  human's ASK gate, or not at all. Plan verification around that.
- **`apply_migration` assigns its own timestamp.** Repo filenames and applied versions no longer match
  (`20260802021757` → applied as `20260802041407`). Same drift `docs/MIGRATION-LEDGER-DRIFT.md` tracks.
  Harmless through the API; it would confuse a `supabase db push` or `db reset`.
- **The E2E suite writes to the production database.** Prefer targeted specs. New fixtures must use the
  `zz-` slug prefix.
- **`is_staff()` must never be redefined.** ~20 policies across listings, photos, features, price
  history, verification events and storage use it to mean "may work the listing panel". Narrowing it
  revokes listing access from the very staff this feature creates. Add a narrower predicate instead —
  that is what `is_super_admin()` is.
- **Column grants on `listings` are table-level**, so any new column inherits `anon` SELECT. That is how
  the price gap exists and how `property_no` inherited it. Assume new columns are public unless you
  detach the grant.
- **`guard_listing_publish` owns "what must be true before live".** Put publish requirements there, not
  in a second trigger — and check the test suite first, because fixtures publish listings.
- **Four agents named in `DISPATCH.md` are NOT installed here:** `plan-critic`, `security-skeptic`,
  `logical-hunter`, `everyday-user`. The 3-lens panel this session ran used installed substitutes
  (`database-architect`, `security-tester`, `general-purpose`) with blindness preserved, and the logic
  hunt ran inline. Registry and install disagree; the registry is meant to win.
- **No peso amounts and no map anywhere public.** Still binding, and see the top of this file for the
  sense in which it is currently *not* true.
- **Commits go straight to `main`.** Push is the release — Vercel deploys in ~20s.
- **Never run `npm audit fix --force`** — it downgrades Next to 9.3.3.
